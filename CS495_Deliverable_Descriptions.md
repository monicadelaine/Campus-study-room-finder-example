# CS 495 LMS Deliverable Descriptions

GitHub is the authoritative project record. LMS submissions are snapshots and links to the current state.

***All submissions are due at 1:30pm***

## 1. Project Setup, Initial Backlog, and Preliminary Presentation (9/3)

**Purpose:** Establish the working engineering environment and show that the team understands the project, sponsor need, initial scope, risks, and first iteration plan.

**Required contents/activities:**

- GitHub repository created and collaborators added, including instructor and TA.
- Standard labels/tags, Project fields, and required Project views created.
- Initial Product Backlog entered as Issues, with priorities and acceptance criteria where ready.
- Setup work represented as Issues and linked to commits/PRs where repository content changes.
- README established as the project landing page with project purpose, team, status, documentation links, GitHub Project link, and course-deliverable links.
- Preliminary presentation exported as PDF and committed under course/presentations/.
- Initial handoff documentation structure created under docs/.
- Course/process structure created under course/.

**Where documented in GitHub:** README.md; repository; GitHub Project; Issues; PRs/commits; docs/; course/; course/presentations/preliminary-presentation.pdf

**Project views to use:** Product Backlog; Current Iteration — planning snapshot; Team Contributions; Engineering & Quality Work; Decisions & Investigations; Remaining Backlog

**What to submit in LMS:**

- Repository URL
- GitHub Project URL
- Preliminary presentation PDF link/path
- Product Backlog snapshot
- Current Iteration — planning snapshot snapshot
- Git tag name if required at checkpoint

**Quality indicators:**

- Initial backlog is not just a wish list; it distinguishes features, setup, documentation, testing, investigations, and risks.
- README provides a clear project landing page and points to the actual GitHub artifacts.
- Preliminary presentation shows actual project state and links to GitHub evidence.

## 2. Preliminary Presentation (9/3)

**Purpose:** Communicate the project problem, sponsor need, current understanding, initial plan, and what decisions are still unresolved.

**Required contents/activities:**

- Project title, team, sponsor/client, and one-sentence purpose.
- Problem/need, users, stakeholders, proposed solution, and initial scope.
- Major Product Backlog themes and highest-priority Issues.
- GitHub Project view showing the initial backlog and Current Iteration — planning snapshot.
- Architecture/technology approach: distinguish decided items from investigations.
- Quality strategy: baseline tests, PR workflow, Definition of Done, documentation expectations.
- Risks/dependencies/unknowns and questions for sponsor.
- Current demonstration of repository, Project, README, tests, or prototype.

**Where documented in GitHub:** PDF committed to course/presentations/preliminary-presentation.pdf and linked from README.

**Project views to use:** Product Backlog; Current Iteration — planning snapshot; Decisions & Investigations; Engineering & Quality Work

**What to submit in LMS:**

- Presentation PDF in LMS or link to committed PDF
- Repository/README link
- Project view screenshots/links used in presentation

**Quality indicators:**

- Presentation reflects actual state; it does not claim functionality that is not implemented.
- Students can explain how Issues, PRs, docs, tests, and Project views connect to the plan.

**Where documented in GitHub:** README.md; docs/; course/presentations/; GitHub Project; final demo-video link.

**Quality indicators:**

- Final video shows working software, not only slides/screenshots.
- Sponsor/future team can understand what was delivered, how to use/deploy/maintain it, and what remains.

## 9. Formal Stand-Up Evidence (Weekly - 1 hour after meeting time)

**Purpose:** Document coordination and provide timestamped evidence of sustained individual contribution and follow-through.

**Required contents/activities:**

- Three documented stand-ups per week.
- At least two of the three occur during scheduled class time.
- One GitHub Issue per meeting.
- Each student posts their own comment during the meeting.
- Comment includes previous commitment/outcome, evidence, work completed, next commitment, blockers/dependencies, collaboration/help, and material AI use if applicable.

**Where documented in GitHub:** GitHub Issues labeled stand-up; individual Issue comments.

**Project views to use:** Stand-Up Issues filter; Team Contributions view for related work

**What to submit in LMS:**

- Links to required stand-up Issues in each iteration submission

**Quality indicators:**

- Comments are contemporaneous and individually authored.
- Commitments are specific enough to evaluate.
- Evidence supports claimed work and connects to Issues, PRs, commits, tests, docs, or sponsor work.

## 10. Responsible AI Use (with issues and PR as needed)

**Purpose:** Allow useful AI assistance while preserving student accountability for all project work.

**Required contents/activities:**

- Disclose material AI assistance where the work occurs: Issue, PR, document, investigation, or stand-up.
- Verify output with tests, review, documentation, experiments, or comparison to requirements.
- Defend the incorporated work: responsible students can explain how and why it works.
- Routine autocomplete/minor wording help does not require detailed disclosure unless it materially shapes the work.

**Where documented in GitHub:** Issue/PR descriptions, docs, stand-up comments, presentations when relevant.

**Project views to use:** Engineering & Quality Work; relevant Issue/PR views

**What to submit in LMS:**

- Highlight significant AI use in iteration submission when it affects major artifacts

**Quality indicators:**

- AI use is transparent, verified, and attributable.
- AI-generated work is not accepted blindly or used to hide lack of understanding.


## Standard GitHub Project Views

Teams create six saved views manually using `GitHub-Project-Views-Student-Instructions.md`: 

- Product Backlog, 
- Current Iteration, 
- Team Contributions, 
- Engineering & Quality Work, 
- Decisions & Investigations, and 
- Remaining Backlog. 

The same Current Iteration view is captured after planning and again at the deadline; the LMS snapshots preserve Plan versus Results.
